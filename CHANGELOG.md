# Changelog

## Unreleased

- Door 4: the local server over HTTP, so claude.ai and the phone can use it with nothing in the org and no Salesforce MCP. `--http <port>` (`SF_REPORTS_HTTP_PORT`) serves Streamable HTTP at `/mcp`, `--host <host>` (`SF_REPORTS_HTTP_HOST`, default `127.0.0.1`) sets the address, and `--public-url <url>` (`SF_REPORTS_PUBLIC_URL`) turns on the server's own OAuth 2.1 sign-in for one owner: dynamic client registration, PKCE, and a passcode page checked against `SF_REPORTS_HTTP_PASSCODE` (at least 16 characters). Tokens are opaque, audience-bound and held as hashes in memory. The steps are in [From claude.ai and your phone](docs/install.md#from-claudeai-and-your-phone), the sequence in [docs/architecture.md](docs/architecture.md), and the reasons in [decision 0020](docs/decisions/0020-door-four-the-local-server-over-http.md).
- The report-runner skill offers a live Claude Dashboard when the person wants a view to keep or share, where the host offers Claude's Dashboard artifacts and `run_report` comes from a connector. Its reference gains the loader recipe, and says that on the local door only a fixed copy is possible ([decision 0021](docs/decisions/0021-claude-dashboards-as-the-shareable-view.md)).

## 0.3.0

Dashboards on every door, the Lightning look on both cards, and a check loop that runs by itself. To upgrade an org on 0.2.0: redeploy `force-app` (it adds `ReportsDashboards` and its test), then `mcp-app`, rerun `npm run mcp:setup -- --org <alias> --yes`, and prove the hosted door with `npm run mcp-login -- --org <alias>` followed by `npm run mcp-check -- --org <alias> --auth <alias>`. The hosted door's dashboard tools call out, so they need `callout-app`, like the other callout tools. Local users only update the package.

- `npm run verify -- --org <alias> [--auth <cli alias>] [--skip <step,...>] [--log <dir>]` runs the whole check loop against one org: `build`, `typecheck`, `test`, the Apex `deploy`, `parity`, `live` (in-org door), `hosted` and a `leftover` query. The first failure stops the run and later steps read `SKIP`; `hosted` reads `SKIP` without `--auth` (a name stored by `npm run mcp-login`). Each step's output goes to a file under the log folder, and the run ends with one markdown table of counts and exits 0 only when nothing failed. The logic is in `scripts/verify-lib.ts`. The deploy and leftover JSON is read even when the CLI prints its update warning after it.
- `npm run mcp-login -- --org <alias> [--auth <name>]` signs in to the hosted door through the External Client App with a PKCE authorization-code flow as a public client (no secret). It reads the consumer key and instance URL from the org through the Salesforce CLI, opens the sign-in page in the default browser, listens on `localhost:1717`, and stores only `{ instanceUrl, clientId, refreshToken }` in `~/.config/salesforce-reports-mcp/auth/<name>.json` (folder 0700, file 0600). Sign out by deleting the file. The CLI's own `--client-app` link cannot complete, because the app does not grant the identity scope it reads ([docs/design.md](docs/design.md), "Hosted door sign-in findings"). The logic is in `scripts/mcp-auth-lib.ts`.
- `npm run mcp-check -- --org <alias> --auth <name>` exchanges the stored refresh token for a fresh access token on every run, so the hosted door can be checked in a loop without a pasted token. The access token is never stored or printed, and a failed exchange reports the HTTP status and `error` field only. `SF_MCP_TOKEN` still works and wins when set; with neither, the error names both. The check expects the fifteen door tools, runs `search_reports` and `run_report`, then `list_dashboards` and, when one is listed, `describe_dashboard` and `run_dashboard`. It refreshes and saves nothing, prints counts only, and ends with `mcp-check: tools=<n> steps=<passed>/<total>`. The logic is in `scripts/mcp-check-lib.ts`.
- The hosted MCP door lists the four dashboard tools, 15 in all: `list_dashboards`, `describe_dashboard`, `run_dashboard` and `refresh_dashboard`, in the order the local server lists them. `refresh_dashboard` joins the save tools in naming the `Reports_Write` permission set in its door description, and says the in-org wait (20 status checks or about 30 seconds) in place of the local 60 seconds. The door drops the dashboard card hint as it drops the report card hint. The registration and server definition are regenerated. To upgrade, redeploy `mcp-app` and rerun `npm run mcp:setup`; on 2026-10-19 all 15 operations answered with no Setup activation, which `npm run mcp-check` proves. The report-runner skill says dashboards are on every door.
- `refresh_dashboard` on the in-org REST door, in `ReportsDashboards`, with the local tool's inputs, output (the `run_dashboard` result after the refresh) and notes. It is a write: it needs the `Reports_Write` custom permission, like the save tools, and a user without it gets 403 `WRITE_NOT_ALLOWED` before any callout. The REST door now has 15 tools. Apex cannot sleep, so the wait polls `/status` back to back, at most 20 times or about 30 seconds, then says in a note that the refresh had not finished and to call `run_dashboard` in a minute ([decision 0019](docs/decisions/0019-refresh-wait-on-the-in-org-door.md)). The once-a-minute 403 becomes the same cached-results note as on the local server, read in `ReportsCallout`. The parity check gains a refresh case on both doors, and the live check runs the refresh on the in-org door.

- [docs/claude-desktop.md](docs/claude-desktop.md): the recipe for the local server in Claude Desktop, with the absolute `node` path and the `PATH` for `sf` that a Dock-launched app needs, how to check it works, the safety flags, the log file, and a table of what each Claude surface can do with a local server. Claude mobile cannot start one, and the page gives the three ways round that with their costs.

- The README leads with the local MCP server: MCP on Salesforce with nothing installed in the org and no Salesforce MCP, a Claude Desktop conversation as the headline, the cards right under it, and the two-command install near the top. The in-org packages are introduced as the same tools rebuilt for people who cannot run a local server. The local door's tool count in the doors table is now 16.

- `npm run typecheck` checks the scripts and tests that `tsc` skips (`salesforce/scripts`, `scripts`, `test`) through `tsconfig.check.json`, and CI runs it after the build. Types only, no change in behaviour: one cast in `salesforce/scripts/org.ts` and one in `test/server.test.ts`.

- Dashboards on the in-org REST door: `list_dashboards`, `describe_dashboard` and `run_dashboard`, in the new core class `ReportsDashboards`, with the local tools' inputs, outputs, notes and errors, the card fields `sourceReport`, `measure`, `metricLabel`, `gauge` and `colorPalette` included. Listing is SOQL on `Dashboard` plus one `/status` callout per row; after a `CALLOUT_*` error the list stops calling `/status` and says so. Describe and run go through `ReportsCallout`, with a filter sent as `filter1`. The `Salesforce_Reports` permission set grants the class, and the removal manifest names it and its test. `refresh_dashboard` and the hosted door's dashboard tools come later. The parity check gains eight dashboard cases against `Pipeline_Overview`, and the live check's dashboard reads run through the door with `--door apex`.
- The report card and the dashboard card follow the Salesforce Lightning Design System: its font stack, type scale, spacing, card border, radius and shadow, brand blue for links and buttons, and its data-visualization palette on every chart. A dashboard that names the Bluegrass, Sunrise, Water or Watermelon palette draws in it, and `DashboardResult` carries the palette name as `colorPalette`. The values are copied from the published token files into one small file inlined at build; no stylesheet, font file or network load, so the cards stay self-contained ([decision 0018](docs/decisions/0018-cards-follow-the-lightning-design-system.md)). At phone width each headline tile takes a row of its own, so a number never breaks across lines.
- The report card shows the answer at a glance: up to three headline tiles (the primary measure's total, the record count, and the largest group's share), a bar beside each group's amount, and for a matrix a heat grid with row and column totals, its full group table folded under "All groups (N)". Currency, dates and percents are formatted, and blanks show a muted dash. Heat cells are shaded in two bands so every cell passes WCAG AA contrast in light and dark. Still inline CSS, no new dependency, and `ReportResult` is unchanged ([decision 0015](docs/decisions/0015-report-card-visuals.md)). Amounts always draw in US dollars, since the result carries no currency code.
- When a card is drawn, the `run_report` and `query_report` descriptions tell Claude to lead with the one finding the card cannot show and never repeat its rows, totals or a table. The report-runner skill says the same for both kinds of host. The hosted door's descriptions are unchanged.
- `npm run test:render` has 11 cases, adding the headline tiles and bars, the matrix heat grid, and the heat grid in dark, and checks formats, bar placement and the contrast of every heat cell. The README GIF is redrawn from the new card.
- Dashboards on the local server: `list_dashboards`, `describe_dashboard`, `run_dashboard` and `refresh_dashboard`. They read and refresh only, and no tool saves a dashboard. `refresh_dashboard` counts as a write, so `--read-only` removes it. A refresh inside a minute of the last one returns the cached results with a note saying when to try again. Filters are given by name and option label ([decision 0016](docs/decisions/0016-dashboards-read-and-refresh-only.md)).
- `run_dashboard` and `refresh_dashboard` carry a dashboard card, a second MCP App at `ui://salesforce-reports/dashboard`. It draws metrics, gauges, donuts, bar, column, line and funnel charts and tables as inline SVG on a grid that follows the dashboard's layout ([decision 0017](docs/decisions/0017-dashboard-card.md)).
- A summary report card draws a column chart of its top-level groups, and at phone width every table folds so nothing scrolls sideways.
- [docs/probes/v0.3-dashboards.md](docs/probes/v0.3-dashboards.md) records how the dashboard REST API lists, refreshes and filters. `npm run capture -- --dashboard <id>` recaptures the dashboard fixtures, and the live check gains four dashboard steps.
- [docs/architecture.md](docs/architecture.md) has a numbered sequence diagram for each door, including the local server and its card, with a table explaining every step.

## 0.2.0

- Published to npm as `salesforce-reports-mcp`. The Claude Code plugin now starts the server with `npx -y salesforce-reports-mcp` instead of building it from GitHub.
- `run_report` and `query_report` on the local server carry a report view, an MCP App at `ui://salesforce-reports/report`, and return the result as `structuredContent` beside the text. Hosts that draw MCP Apps, such as Claude Desktop, show the run as a report card: the title, the filters, the groups with totals, a link to Salesforce and, for an unsaved report, a button that asks Claude to save it. The view loads nothing from the network ([decision 0013](docs/decisions/0013-report-view-as-an-mcp-app.md)). The two descriptions tell Claude not to repeat the card's table; the hosted door's descriptions leave that line out, since it draws no card.
- `npm run test:render` draws the view in Chromium through a test host with the real host bridge and compares screenshots in light, dark and at 360 px, for summary, matrix and tabular results. CI runs it on Linux. `npm run demo:gif` makes the README's demo from the same page ([decision 0014](docs/decisions/0014-render-tests-through-a-test-host.md)).
- Corrected: Opportunity's default standard filter `probability: >0` is Salesforce's "All" and does not hide Closed Lost. The skills and docs said it did.
- `npm run callout:renew -- --org <alias>` renews the callout certificate behind the hosted door's named credential, with no Setup screens and no user clicks: the org makes a new key pair, the app and the external credential move to it in one deploy, and the old certificate is removed. Assignments are untouched. Run it in the month before the expiry, which `callout:setup` and the renewal now print ([decision 0012](docs/decisions/0012-per-user-jwt-named-credential.md)).
- `run_report` and `query_report` say in `notes`, on every door, when Salesforce ignored a `reportMetadata.standardFilters` override: an empty list does not clear a report's standard filters, so the note names the ones that still apply, and a partial list leaves the rest at their saved values. A standard filter can only be given another value by name ([live finding](docs/design.md#live-findings-checked-2026-10-11-api-v620-scriptslive-checkts)). Deploy `force-app`.
- The hosted MCP door can run the callout tools as the signed-in user: `list_report_types`, `query_report`, `combine_reports` with definitions, the full `describe_report_type` and the three saves. A new optional package, `salesforce/callout-app`, holds a per-user JWT named credential, `SalesforceReportsCallout`, its External Client App and certificate, and the permission set `Salesforce_Reports_Callout`, with no code ([decision 0012](docs/decisions/0012-per-user-jwt-named-credential.md), Accepted after a call from claude.ai). On the hosted route `ReportsCallout` calls out through it and never asks for a session. Without the package, the hosted route answers `CALLOUT_SESSION` as before. With it, a user without the permission set gets the new code `CALLOUT_CREDENTIAL`, with a hint naming the set. The REST route is unchanged. To use it, deploy `force-app`, run `npm run callout:setup -- --org <alias>`, which fills My Domain, the consumer key and the certificate into a temp copy and deploys it, and assign the permission set. It has its own removal manifest in `salesforce/manifest/callout-app/`.
- A call with no arguments works on both in-org routes. The hosted server most likely posts a JSON `null` body for it, which the door refused with `INVALID_INPUT`. The door now reads `null` as no input, as the local server reads missing arguments. Deploy `force-app`.
- The hosted MCP door has its own route, `/services/apexrest/reports/v1/mcp/<tool>`. A hosted sign-in gives Apex no session, and asking for one threw an exception Apex cannot catch, so the client saw a raw `APEX_ERROR`. On the new route the callout tools answer `CALLOUT_SESSION` before they ask for a session, and the skills' fallback runs ([decision 0007](docs/decisions/0007-callout-identity-under-hosted-mcp.md), now Accepted). The REST door stays at `/reports/v1/<tool>`. To upgrade, deploy `force-app`, then the registration and the server in `mcp-app`.
- The permission sets and the custom permission are renamed for the capability, not the door ([decision 0011](docs/decisions/0011-name-permissions-for-the-capability.md)): `Salesforce_Reports_MCP` is `Salesforce_Reports`, `Salesforce_Reports_MCP_Write` is `Salesforce_Reports_Write`, and `Reports_MCP_Write` is `Reports_Write`. An org that installed the earlier names deploys `force-app`, assigns the two new sets to the same users, removes the old assignments, then deletes the old sets (pre step) and the old custom permission (post step) with a destructive deploy.
- `salesforce/` is now two package directories. `force-app` is the REST door alone: the classes, the two permission sets and the custom permission. `mcp-app` holds the hosted MCP door on top of it: the API Catalog entry, the MCP server and the External Client App (moved from `salesforce/eca`), and no code. Deploy `mcp-app` after `force-app`. Each has its own removal manifest in `salesforce/manifest/`, and the MCP door is removed first. `test/packages.test.ts` keeps the split in CI. On the door, `create_report`, `update_report` and `clone_report` now say they need the permission set `Salesforce_Reports_Write`. `ReportsApi` drops its `baseUrl()` and `DEFAULT_MAX_ROWS` pass-throughs.
- v0.2 phase 3b: the in-org door adds `create_report`, `update_report` and `clone_report`, through `ReportsCallout`. They need the new permission set `Salesforce_Reports_Write` (custom permission `Reports_Write`) and answer 403 `WRITE_NOT_ALLOWED` without it. The hosted server now carries eleven tools; run `npm run mcp:setup` after deploying to add the three new tool rows. `delete_report` stays local-only.
- v0.2 phase 3a: the in-org door adds `list_report_types` and `query_report`, `describe_report_type` gains filter operators and types with no saved report, and `combine_reports` takes definition inputs. All three call the org's own REST API through one Apex helper, `ReportsCallout`. The hosted server now carries eight tools; run `npm run mcp:setup` after deploying to add the two new tool rows.
- `mcp:setup` and `mcp:teardown` take any org you name: pass `--yes`, or set `SF_REPORTS_SETUP_ORGS` to the aliases they may change (an alias off that list is refused even with `--yes`). No alias is hard-coded, and both print the alias and instance URL before they write.
- v0.2 phase 2, the in-org MCP door: `salesforce/` adds the API Catalog entry `ReportsApi` (one operation per tool, schemas generated from the local server by `npm run mcp:generate`), the hosted MCP server `SalesforceReports` with the six read tools, a permission set, `npm run mcp:setup` and `mcp:teardown`, an External Client App for sign-in, and `npm run mcp-check`. The README's "In the org" section has the admin steps.
- v0.2 phase 1, the in-org REST door: `salesforce/` holds `ReportsApi`, an Apex REST class at `/services/apexrest/reports/v1/<tool>` for search_reports, list_report_folders, describe_report, describe_report_type, run_report and combine_reports, with the local server's inputs and results. `npm run parity` checks both doors give the same JSON, and `npm run live -- --door apex` runs the read steps through it.
- The Salesforce CLI now starts on Windows: `sf.cmd` runs through a shell with the org alias checked first, and a failure to start the CLI says how to fix it.
- Three skills replace `skills/salesforce-reports`: `report-runner` (explore and answer, never saves), `report-designer` (change or make a report, preview, save) and `report-deploy` (move a saved report between orgs or into git with the Salesforce CLI).
- A Claude Code plugin: `.claude-plugin/plugin.json` and `marketplace.json`, bundling the skills and the server through `npx -y github:nelsben/salesforce-reports-mcp`, with no org baked in.
- `create_report` takes `fromReportId`: copy a saved report, apply the changes given, and save as new.
- `describe_report` returns `developerName` and the folder as `{id, name, developerName, isPrivate}`.
- `list_report_folders` includes the org-wide Public Reports folder (`unfiled$public`; its id is the org id).
- `docs/experiences.md` records three live probes: standard column headers cannot be renamed through the REST API but a row-level formula column can carry a label; the Metadata API cannot retrieve a report in Private Reports; bucket fields and cross filters are accepted with the shapes listed there.
- `docs/rehearsals/` holds headless runs of each skill.

## 0.1.0

First release.

- Twelve tools over the Salesforce Reports and Dashboards REST API: `search_reports`, `list_report_folders`, `list_report_types`, `describe_report_type`, `describe_report`, `run_report`, `query_report`, `combine_reports`, `create_report`, `update_report`, `clone_report` and `delete_report`.
- One result shape for every run (`ReportResult`): filters in words, a tidy group table, grand totals, optional detail rows, and notes that say when rows were cut.
- `combine_reports` stacks or joins 2 to 5 runs, for period comparisons and side-by-side measures.
- Authentication through the Salesforce CLI (`--org`) or an access token you already hold (`SF_INSTANCE_URL`, `SF_ACCESS_TOKEN`).
- Safety flags: `--read-only` registers no write tools; `delete_report` exists only with `--allow-delete`; new reports are saved to Private Reports.
- A Claude skill, `skills/salesforce-reports`, that teaches the workflow.
- Live-verified against a Developer Edition org (API v62.0): aggregate prefixes, date-granularity values, and three Salesforce rules about detail columns are recorded in `docs/design.md`.
