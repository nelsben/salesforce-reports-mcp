# v0.2 phase 2: the hosted MCP door

Run on 2026-10-11 against `dev-frontend-2`: a Developer Edition scratch org, API 68.0, expires 2026-11-01. The source is in `salesforce/`, and the admin steps are in the repo README, section "In the org". The server, its tools, the API Catalog entry and the permission set stay deployed and active in `dev-frontend-2` for Ben's sign-in.

## Summary

| Question | Answer |
| --- | --- |
| Do the tool rows get written by a script? | Yes. `npm run mcp:setup -- dev-frontend-2` wrote six `McpServerToolDefinition` rows and six `McpServerToolApiDefinition` rows, and a second run changed nothing. |
| Which `ApiSource` and `ApiIdentifier` work? | `API_CATALOG` and `ar:ReportsApi`, with `Operation` equal to the tool name. |
| Are the tools metadata after all? | Yes, at API 68.0. A retrieve of `McpServerDefinition` returns a `<tools>` element per tool. Phase 0 read only `description`, `masterLabel` and `fullName` from `describeValueType`. The committed server now carries its six tools, so a deploy alone writes the rows. |
| How does the server become active? | An `McpServerAccess` row with `Active` true and `McpServerId` set. The setup script writes it. |
| How do the operations become active? | Only in Setup. The API Catalog shows all six as inactive, and no API changes that. Whether the hosted server needs them active is open until a signed-in call. |
| What is the endpoint? | `https://api.salesforce.com/platform/mcp/v1/sandbox/custom/SalesforceReports`, read from the API Catalog. |
| Does a headless token work? | Not tested to the end. The org will not hand out an External Client App's consumer secret over REST, so no client credentials token was issued. The CLI token gets 401 "Invalid token". |
| What do the hosted tool names and input schemas look like? | Open. `tools/list` needs a signed-in token. The tool rows hold the exact names. |

## What was deployed

| Component | Name | Notes |
| --- | --- | --- |
| `ExternalServiceRegistration` | `ReportsApi` | `ApexRest`, `systemVersion` 3, inline OpenAPI 3.0 at base path `/services/apexrest`, one POST per tool at `/reports/v1/<tool>`, `operationId` equal to the tool name. Status `Complete` on the first deploy. 50 KB. |
| `McpServerDefinition` | `SalesforceReports` | Label "Salesforce Reports", six `<tools>`. |
| `PermissionSet` | `Salesforce_Reports_MCP` | Apex class access to `ReportsApi`, `ReportsCombine`, `ReportsDefinition`, `ReportsShape`, `ReportsSummary`. There is no MCP permission to grant: the only `PermissionSet` field with MCP in its name is `PermissionsMCPMetadataApi`, which is for the Metadata API. |
| `ExternalClientApplication` | `SalesforceReportsMcp` | In `salesforce/eca/`. Checked with a dry run only. It is for Ben's sign-in, so it is not deployed. |

`npm run mcp:generate` writes the registration and the server from the local server's tool list, so the names, descriptions and input schemas come from `src/server.ts`. The input schemas go into OpenAPI 3.0 with three changes: `$ref` pointers are inlined (`run_report` and `combine_reports` reuse `overrides`), a type list such as `["string","number","boolean"]` becomes `anyOf`, and `$schema` is dropped. `--check` fails when a committed file is stale.

## Findings

### The tool rows

The Tooling describe of `McpServerToolApiDefinition` gives `ApiSource` as one of `CONNECT`, `CLASSIC`, `API_CATALOG`, `AGENT`, and `ApiIdentifier` and `Operation` as required strings of 255. `McpServerToolDefinition` adds `ReturnDirect` and `UiResource` to the fields phase 0 listed, and `DescriptionOverride` holds 1,024 characters. The longest tool description is 565.

| Try | Result |
| --- | --- |
| `API_CATALOG`, `ar:ReportsApi`, `search_reports` | Created |
| `API_CATALOG`, `ar:ReportsApi`, `bogus` | `FIELD_INTEGRITY_EXCEPTION: No operation "bogus" found for identifier "ar:ReportsApi" from source "API_CATALOG". Valid operations for this identifier are [run_report, describe_report_type, search_reports, list_report_folders, combine_reports, describe_report]` |

So the operation is the `operationId` as written, not the `x5f` form in the registration's `<operations>`. The validator accepts it while the operation is inactive. The `ar:` prefix came from a public write-up of the identifier shapes Setup generates; the validator's answer confirms it.

### The API Catalog

`GET /services/data/v68.0/api-catalog/apis` lists the registration and the server:

```
{"id":"0LeAs000000581l","label":"ReportsApi","providerType":"APEX_REST","properties":{}}
{"id":"1g1As00000004ZtIAI","label":"Salesforce Reports","providerType":"PLATFORM_CUSTOM_MCP_SERVER",
 "properties":{"serverUrl":"https://api.salesforce.com/platform/mcp/v1/sandbox/custom/SalesforceReports","isActive":false}}
```

`isActive` turned true once the `McpServerAccess` row was written. `GET .../api-catalog/sources/APEX_REST/apis/<id>/versions/<id>/operations` lists the six operations with `name` equal to the tool name, `resource` `/reports/v1/<tool>`, method `POST`, an id starting `1XO`, and `isActive` false.

### Activation

| What | How | Result |
| --- | --- | --- |
| Server | `POST tooling/sobjects/McpServerAccess` with `DeveloperName` `SalesforceReports`, `MasterLabel`, `Active` true, `McpServerId` | Created. The catalog says active. |
| Operations, by deploy | `<active>true</active>` in the registration | Deploys, reads back false (as in phase 0) |
| Operations, by Tooling | `PATCH tooling/sobjects/ExternalServiceRegistration/<id>` with `Metadata.operations[].active` true | `UNKNOWN_EXCEPTION` each time. The same PATCH without `operations` succeeds. |
| Operations, by API Catalog | `PATCH`, `PUT` and `GET` on `.../operations/1XO...` | `NOT_FOUND` |

The operations stay inactive. If a signed-in call fails because of that, the fix is in Setup: API Catalog, `ReportsApi`, select the six operations, Activate.

### Deploys and the tool rows

| Action | Tool rows after |
| --- | --- |
| Deploy the server without `<tools>` while it had six rows | 0. A deploy replaces the server's tool list. |
| Deploy the registration alone | 6, unchanged |
| Deploy the server with its six `<tools>` while active | 6, and the server stays active |
| Delete the server while active | Refused: `Server must be inactive before making changes` |
| Delete the class `ReportsApi` before the registration | Refused: `This apex class is referenced elsewhere in Salesforce ... External Service Registration - ReportsApi` |

So the server source carries its tools, the removal manifest deletes the registration, server and permission set in a pre step and the classes in a post step, and teardown runs first.

A from-scratch rehearsal in `dev-frontend-2` ran the whole path: teardown, the pre-step removal (server, registration and permission set deleted, `McpServerToolDefinition` empty), `sf project deploy start -d force-app` (six rows written by the deploy), then setup (rows unchanged, server access created and active). The deploy needed `--ignore-conflicts` because source tracking still held the phase 1 deploy of the classes, which were unchanged.

### The headless token

| Step | Result |
| --- | --- |
| CLI access token at the endpoint | `HTTP 401 {"errors":[{"message":"Invalid token"}]}` |
| Temporary External Client App `ReportsMcpCheck`: client credentials on, run-as the scratch admin, scopes `MCP`, `Api`, `RefreshToken`, `isNamedUserJwtEnabled` true | Deployed. `ExtlClntAppOauthPlcyCnfg` shows `IsClientCredentialsFlowEnabled` true and the run-as user set. `apps/oauth/usage` still reports `accessTokenFormat` "opaque". |
| Read the consumer secret: `GET /services/data/v68.0/apps/oauth/credentials/<app>/<consumer>?part=keyandsecret` | HTTP 200 with `id`, `key`, `name`, `url`, and no secret. `?part=secret` returns no key and no secret. The org setting `ExternalClientAppSettings.enableClientSecretInRestApiAccess` is false. |
| Token request with the key and no secret | `HTTP 400 {"error":"invalid_client","error_description":"invalid client credentials"}` |

I stopped there. Turning on `enableClientSecretInRestApiAccess` is an org security setting the card did not approve, and copying the secret from Setup needs a person. The temporary app was removed with a destructive deploy, and only `Plesio_Claude`, which was there before, remains.

To finish the test, Ben can approve turning that setting on for the test and off afterwards, or copy the secret into a shell variable himself. A public write-up of hosted MCP says it takes only authorization code tokens, so the likely answer is that a client credentials token is refused too.

### Smaller findings

- The custom server's `DeveloperName` cannot have an underscore. The URL keeps its case.
- A sandbox or scratch org uses `/platform/mcp/v1/sandbox/custom/<Server>`. Phase 0 tried the form without `sandbox/`.
- `ExternalServiceRegistration` takes a 50 KB inline schema.
- `sf api request rest ... --body @file` sends a file body.

## Ben's sign-in

Run these from a terminal, after this branch is merged. `sf project deploy start` only runs inside the SFDX project, so step 1 enters it in a subshell.

1. Deploy the External Client App.

   ```bash
   (cd /Users/bennelsen/Documents/salesforce-reports-mcp/salesforce && sf project deploy start -d eca -o dev-frontend-2)
   ```

2. Read its consumer key (a client id, not a secret). Run the query, then pass the Id it prints to the second command.

   ```bash
   sf data query -t -q "SELECT Id FROM ExternalClientApplication WHERE DeveloperName = 'SalesforceReportsMcp'" -o dev-frontend-2
   sf api request rest "/services/data/v68.0/apps/oauth/credentials/<app id>" -o dev-frontend-2
   ```

3. Open the scratch org in your default browser, the one you use for claude.ai, and stay logged in. Log out of other Salesforce orgs in that browser first.

   ```bash
   sf org open -o dev-frontend-2
   ```

4. In claude.ai, open Settings, then Connectors, then Add custom connector. Name it "Salesforce Reports (dev-frontend-2)" and use the URL `https://api.salesforce.com/platform/mcp/v1/sandbox/custom/SalesforceReports`. Under Advanced settings, paste the consumer key as the OAuth Client ID. Click Add, then Connect, and allow access.
5. If the connector lists no tools, or a call fails with an inactive-operation error, open Setup in the scratch org, go to API Catalog, open `ReportsApi`, select all six operations, and click Activate. Then reconnect.
6. Add the runner skill. Zip the folder (with the folder at the top of the zip), then upload the zip in claude.ai under Settings, then Capabilities, then Skills.

   ```bash
   ditto -c -k --keepParent /Users/bennelsen/Documents/salesforce-reports-mcp/skills/report-runner /Users/bennelsen/Downloads/report-runner.zip
   ```

7. In a new chat with the connector and the skill on, ask: "What reports do I have about opportunities? Run the first one." The answer should name a report from `search_reports` and show the result of `run_report`.
8. Optional, from a terminal: put an access token from that sign-in into `SF_MCP_TOKEN` and run the check. It lists the tools and calls `search_reports` and `run_report`.

   ```bash
   npm --prefix /Users/bennelsen/Documents/salesforce-reports-mcp run mcp-check -- --org dev-frontend-2 --dump /Users/bennelsen/Downloads/hosted-tools.json
   ```

Done looks like this: the connector lists exactly the six tools, the chat answers from a real report, and the findings above can record the hosted tool names and input schemas from `hosted-tools.json`.
