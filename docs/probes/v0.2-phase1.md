## Parity

`scripts/parity-check.ts` creates three private reports through the local server (`zz-parity-tabular-*`, `-summary-*`, `-matrix-*`, Opportunity type), runs each case through the local server and through `POST /services/apexrest/reports/v1/<tool>`, and compares the two JSON bodies with a deep equal.

| Tool | Cases | Result |
| --- | --- | --- |
| `run_report` | tabular, summary and matrix as saved; summary and matrix with detail rows; tabular without detail rows; overrides with a filter, a grouping change, a column change, and a date filter with new aggregates and filter logic; a `maxRows` cut | 11 of 11 equal |
| `describe_report` | tabular, summary, matrix | 3 of 3 equal |
| `search_reports` | by name, by name and format with a limit, the most recent | 3 of 3 equal |
| `list_report_folders` | all, search "public" | 2 of 2 equal |
| `combine_reports` | stack of grouped results, stack of detail rows with `maxRows`, join | 3 of 3 equal |
| `describe_report_type` | Opportunity with a search, Opportunity with a limit | 2 of 2 equal, leaving out `filterOperators` and `notes` |
| Door contract | `query_report` answers 404 `UNKNOWN_TOOL`; an unknown tool answers 404; a bad report id answers 400 `INVALID_INPUT` | 3 of 3 |

Before the classes were deployed, every case failed with HTTP 404 `Could not find a match for URL`.

Not at parity, by design:

- **`describe_report_type`** comes from `describeReport(...).getReportTypeMetadata()` on a saved report of the type. Apex has no operator map, so `filterOperators` is `{}` and a note lists the common operators. Apex also has no `dateGranularityInfos`. REST lists the same nine for every type checked (Opportunity, AccountList), so the door returns that list.
- **`describe_report` with `includeMetadata`** returns the `reportMetadata` fields Apex exposes. REST-only fields (`chart`, `dashboardSetting`, `presentationOptions`, `saveRoleHierarchy`, `supportsRoleHierarchy`, `userOrHierarchyFilterId`) are absent.
- **Errors** carry the same `{"error": {code, message, hint}}` shape, but the codes come from Apex exceptions (for example `INVALID_FILTER` from `Reports.InvalidFilterException`), not REST error codes.
- **Report links** are built from `URL.getOrgDomainUrl()`. In `dev-frontend-2` it is the same `*.scratch.my.salesforce.com` host as the CLI's instance URL, so every `url` matched.

## Heap and CPU

`salesforce/scripts/measure.apex` runs saved reports through the door's own code, as `runToResult` does: `ReportManager.runReport`, then `ReportsShape.shapeResult` at the default 200 rows, then the JSON body. Limits inside the run: heap 10,000,000 (the documented synchronous limit is 6 MB; plan against 6 MB) and CPU 10,000 ms.

**The data limits the runs.** `dev-frontend-2` has 9 opportunities, and the largest object counted has 98 records (`Detected_Signal__c`), yet the report over it still returned one row per opportunity. The card forbids creating records. So the reports below have 9 rows, and longer runs are stood in for by keeping k real runs in heap at once.

Each run alone (`zz-parity-measure-*`, type Opportunities with Detected Signals, 9 rows):

| Columns | Cells | Heap after run | After shaping | After the body | Body bytes | CPU ms: run | After shaping | After the body |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 90 | 5,763 | 8,691 | 10,128 | 3,019 | 40 | 47 | 50 |
| 50 | 450 | 19,074 | 26,050 | 29,009 | 9,937 | 51 | 65 | 73 |
| 100 | 900 | 33,913 | 44,707 | 49,883 | 17,560 | 68 | 94 | 107 |

Per cell: about 35 bytes for the run result, 10 for the shaped rows and 5 for the body, and 0.07 ms of CPU on top of about 44 ms per run.

| --- | --- | --- | --- |
| 1 | 900 | 52,787 | 108 |
| 2 | 1,800 | 100,222 | 211 |

Heap is linear at 52.7 bytes per cell. Peak heap adds the JSON string while it becomes the body, about 20 bytes per cell, so about 73 bytes per cell in all. Phase 0 estimated 105: the port builds only the rows it returns.

| Case | Cells | Heap at the end | Peak heap | CPU |
| --- | --- | --- | --- | --- |
| Default: 200 rows, 100 columns | 20,000 | 1.05 MB (measured 0.95 MB at 18,000 cells and 1.14 MB at 21,600) | about 1.5 MB | 1.4 to 2.6 s |
| Ceiling: 500 rows by 100 columns, or 2,000 by 25 | 50,000 | about 2.6 MB | about 3.6 MB | 3.5 to 6.4 s |

The low CPU figure is the per-cell slope of one run; the high one is the k-run figure, which pays the 44 ms per-run cost k times.

**The cap is confirmed.** `min(2000, floor(50000 / columns))` keeps the peak near 3.6 MB of 6 MB and CPU under 10 s. Heap alone would allow about 80,000 cells, but CPU would then reach 5.6 to 10 s, so 50,000 stays. A real 200-row run still needs an org with more data than `dev-frontend-2`.

The door also checks heap: past 80% of the limit it stops with `RESULT_TOO_LARGE` and a hint to narrow filters or lower `maxRows`, because Apex cannot catch the heap limit itself. There is no async fallback in phase 1.

## Findings

- **`Report.ReportTypeApiName` is not the REST type name, and SOQL does not filter on it.** For the Opportunity reports here it reads `Opportunity@Opportunity.Strategy_Framework__c` (the org has a custom lookup on Opportunity), while REST and `describeReport` say `Opportunity`. `WHERE ReportTypeApiName = 'Opportunity'` and `LIKE 'Opportunity%'` both return no rows. The door scans up to 10,000 recently modified reports for the name or the name followed by `@`, then checks the type with `describeReport` (at most five).
- **Apex `ReportMetadata` has no `folderId`.** `Report.OwnerId` is the same 18-character id REST returns: the owner's user id for Private Reports, a folder id otherwise.
- **Cell values in Apex:** currency is a `Reports.ReportCurrency` (`getAmount()`), percent and numbers are `Decimal` or `Integer`, dates are `Date`, lookups are `Id` with the name in the label. In Apex a `Date` is an instance of `Datetime`, but a `Datetime` is not an instance of `Date`, so the shaper tests `Date` first.
- **Datetime cells** are written as `YYYY-MM-DDThh:mm:ssZ`. The Opportunity type has no datetime column, so this is not checked against REST yet.
- **Apex enums differ from REST names:** `ASCENDING` and `DESCENDING` are `Asc` and `Desc`, `FISCAL_QUARTER` is `FiscalQuarter`, `CURRENCY_DATA` is `currency`. The door maps them both ways.
- **Exception type names in the `Reports` namespace come back in lower case** (`reports.InvalidFilterException`).
- **`sf project deploy start` must run inside the SFDX project**, so the commands in `salesforce/README.md` run from `salesforce/`.

