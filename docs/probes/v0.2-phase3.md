# v0.2 phase 3a: the callout tools on the in-org door

Run on 2026-10-11 against `dev-frontend-2`: a Developer Edition scratch org, API 68.0, expires 2026-11-01. The source is in `salesforce/`. Phase 0 probe 3 showed that Apex can call the org's own Reports REST API under a user session with no Remote Site Setting. Phase 3a uses that to bring `list_report_types`, `query_report` and a full `describe_report_type` to the in-org door. Saves (create, update, clone) follow in phase 3b on the same helper.

## What was built

| Piece | What it does |
| --- | --- |
| `ReportsCallout` (new) | The one call to the org's REST API. A missing session, a 401, or the code `INVALID_SESSION_ID` throws `CALLOUT_SESSION` (HTTP 500) with the hint "The in-org door could not call the org's REST API under this sign-in." Any other Salesforce error throws what `src/salesforce/client.ts` and `src/format.ts` build: Salesforce's `errorCode` (else `error`, else `HTTP_<status>`), its `message` (else `error_description`), the same hint, and HTTP 400 for a 4xx, else 500. A call that fails outright throws `CALLOUT_FAILED`. Before parsing, it stops with `RESULT_TOO_LARGE` if the body would not fit the heap. |
| `list_report_types` | `GET /analytics/reportTypes`, summarized as `src/reports/summarize.ts` does, with `search` and `limit`. |
| `describe_report_type` | `GET /analytics/reportTypes/{type}`, summarized as the local tool does, with filter operators. It works for a type nobody has saved a report of. On `CALLOUT_SESSION` it falls back to the phase 1 path (through a saved report of the type) and says so in two notes: one for the fallback, one for the missing filter operators. |
| `query_report` | Maps the definition with `ReportsDefinition.toReportMetadata(def, false)`, adds a detail column to a grouped report that has none (as the local `ensureDetailColumn` does, from the type's default columns), posts to `/analytics/reports/query`, and shapes the REST JSON. It uses the in-org row cap `run_report` uses, `min(2000, floor(50000 / columns))`. |
| `combine_reports` | A `definition` input now runs through `query_report`. |
| `ReportsShape` | One shared shaper. A frame builds the header, dimensions, measures, row budget, detail table and notes once. Two walkers fill it: `shapeResult` reads `Reports.ReportResults` (run_report), and `shapeJson` reads the REST JSON (query_report), a JSON port of the factMap walk in `src/reports/shape.ts`. `cell` now also reads the REST currency cell `{"amount", "currency"}`. |
| `ReportsSummary` | `infoMapsJson`, `summarizeReportTypes` and `summarizeReportTypeJson`, ports of the local functions over the REST JSON. |
| Permission set | Adds `ReportsCallout`. The destructive manifest names `ReportsCallout` and `ReportsCalloutTest`. |
| `salesforce/scripts/measure-query.apex` | Measures the callout time and heap of a `query_report` with detail rows. |

### Deviations from the local server

| Where | Difference | Why |
| --- | --- | --- |
| `query_report` | It asks Salesforce for detail rows only when the result will show them (`detail`, else a tabular format). The local server asks unless `detail` is false. The shaped result is the same, with one exception: for a grouped query over 2,000 rows without `detail`, Salesforce sets `allData` false only when detail rows were asked for, so the local note "Salesforce stopped at 2,000 rows" can be missing on the door. | Detail rows the result drops would still cost heap. |
| Errors | A refused session answers `CALLOUT_SESSION`, where the local server answers 401 with its sign-in hint. A failed call answers `CALLOUT_FAILED`. | The door has no sign-in of its own to renew. |

## Measured: a query_report with detail rows

`sf apex run -f salesforce/scripts/measure-query.apex -o dev-frontend-2`. It makes the same call `queryToResult` makes, through `ReportsCallout.send`, then shapes the result, then runs the whole tool through `ReportsApi.handle`. Anonymous Apex here reports a heap limit of 10,000,000 bytes and a CPU limit of 10,000 ms. A REST request has the synchronous 6 MB heap.

| Case | Rows | Columns | Callout and parse | Heap after parse | Shape | Heap after shape | Response | CPU |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| tabular, 8 columns, maxRows 2000 | 8 | 8 | 1,852 ms (first call) | 10,089 B | 40 ms | 12,943 B | 1,661 B | 28 ms |
| summary by stage, 8 columns, detail rows | 8 | 8 | 283 ms | 10,728 B | 5 ms | 13,448 B | 2,203 B | 22 ms |
| `ReportsApi.handle('query_report', ...)`, the tabular case | 8 | 8 | 275 ms for the whole tool | 2,126 B | | | | |

`dev-frontend-2` holds only 9 opportunities, so these numbers show the overhead, not a large report. The first callout of a transaction cost about 1.9 seconds; later ones cost under 300 ms. For size, the phase 3a probes of `GET /analytics/reportTypes/Opportunity` give the scale: 67,428 characters cost 135,773 bytes of heap as a string (about 2 per character) and 51,877 more once parsed. So a REST body costs about 3 bytes of heap per character. With the 6 MB heap and the 80% guard, a query body of roughly 1.5 million characters is the most the door can take. `ReportsCallout` checks that before parsing and answers `RESULT_TOO_LARGE`, and Apex refuses a response over 6 MB with `CALLOUT_FAILED`. The row cap keeps the shaped result itself small, but the cap applies after Salesforce sends up to 2,000 rows, so a wide grouped query with detail rows is the case to watch.

## Open: does the callout work under a hosted MCP sign-in?

The local check runs the door under a CLI session, which has full API access. A claude.ai sign-in goes through the External Client App `SalesforceReportsMcp`, whose scopes are `mcp_api` and `refresh_token` only. Whether a session born of that token may call `/services/data/...` from Apex is the open question. Nothing here can answer it without a signed-in user.

### Ben's steps

1. In claude.ai, open a chat with the SalesforceReports connector on (the one connected in phase 2 to `dev-frontend-2`). If it is not connected, follow steps 6 and 7 of "In the org" in the repo README first.
2. If the connector does not list `list_report_types` and `query_report`, open Settings, then Connectors, then SalesforceReports, and reconnect. If tools still fail as inactive, open Setup in the scratch org, go to API Catalog, open `ReportsApi`, select all eight operations, and click Activate. Then reconnect.
3. Ask: "Using the SalesforceReports connector, call list_report_types with search opportunit." Done looks like a list that includes the type `Opportunity`.
4. Then ask: "Call query_report with reportType Opportunity, groupingsDown STAGE_NAME and aggregates RowCount." Done looks like a group table by stage.
5. Write down the answer of step 3: a list of types, or an error with its code.

### What CALLOUT_SESSION would mean

An answer with code `CALLOUT_SESSION` means the Apex ran, but the org's REST API refused the session it got from the hosted sign-in: no session at all, a 401, or `INVALID_SESSION_ID`. The phase 1 tools still work, because they do not call out. `describe_report_type` falls back to reading the type through a saved report, and says so in its notes. `list_report_types` and `query_report` cannot work until one of the fixes below is in. Another refusal code from Salesforce, for example a 403, would be the same problem in another form and shows up with that code.

### Two fixes to try

Do not change the External Client App without Ben's yes. Neither fix is made here.

1. **Add the `Api` scope to the External Client App.** In `salesforce/mcp-app/main/default/extlClntAppOauthSettings/SalesforceReportsMcp.ecaOauth-meta.xml`, `commaSeparatedOauthScopes` becomes `MCP, Api, RefreshToken`. Deploy `mcp-app`, then reconnect in claude.ai so the new token carries the scope. What it widens: the token Claude holds would be good for the whole REST and SOAP API as that user, not only the MCP endpoint. Anything holding the token could then run SOQL and read or write any record the user can, outside the eight tools. Sharing, field-level security and the user's permissions still apply. It is the smallest change, and the broadest grant.
2. **A per-user Named Credential.** An External Credential with the OAuth browser flow and per-user principals, pointing at a second External Client App or Connected App that has the `Api` scope, and a Named Credential on the org's own domain. Each user authenticates once (in their personal settings, under External Credentials), and needs a permission set that grants the principal. `ReportsCallout` then sets the endpoint to `callout:<name>` plus the path and drops the `Authorization` header. That one class is the only change in code. What it widens: only Apex that uses the Named Credential can use the API grant, and the MCP token stays `mcp_api` only. The cost is a setup step per user and more metadata.
