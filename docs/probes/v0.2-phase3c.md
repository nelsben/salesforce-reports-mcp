# v0.2 phase 3c: a per-user JWT named credential back into the same org

Run on 2026-10-12 against `dev-backend`: a Developer Edition scratch org, API 68.0. The source is in `probes/v0.2-named-credential/`. Nothing in `src/` or `salesforce/` changed.

Under a hosted MCP sign-in, `UserInfo.getSessionId()` throws, so the hosted door refuses the callout tools with `CALLOUT_SESSION` ([decision 0007](../decisions/0007-callout-identity-under-hosted-mcp.md)). The remedy chosen is a per-user named credential. Research recommended the OAuth JWT bearer flow with a per-user principal: no consumer secret and no per-user click. No source confirmed that it works against the org that issues the token. This probe tests that.

Labels: **observed** means seen in `dev-backend` in this run. **Inferred** means reasoned from what was seen, not tested.

## Summary

| Open item | Answer | Label |
| --- | --- | --- |
| 1. Does same-org per-user JWT work? | Yes. Anonymous Apex called `callout:SalesforceReportsSelf/...` and the org minted a token for the running user from its own token endpoint, with no session and no click. Both identity calls named the running user. | observed |
| 2. Does the External Client App's OAuth settings file with a certificate deploy with `sf project deploy`? Can it be set without reading a consumer secret? | Yes to both. `ExtlClntAppGlobalOauthSettings` with `<certificate>` was created by `sf project deploy start`, from a source folder. The consumer key comes from a REST listing that holds no secret. No consumer secret was read, retrieved or written, and no org setting was turned on. | observed |
| 3. Do Reports API calls succeed through the credential? | Yes. `analytics/reportTypes`, `analytics/reports`, `analytics/reports/<id>/describe` and a report run (`analytics/reports/<id>?includeDetails=false`) all answered 200. | observed |
| 4. What manual steps does an admin still need? | Run the setup (one script) and assign the permission set to each user who needs the callout tools. Renew the certificate once a year. No per-user click, no secret to paste, no Setup screen. | observed for setup and assignment; renewal inferred from the certificate's expiry date |
| Does it work from a hosted MCP sign-in? | Untested here. This run used the CLI's session in anonymous Apex. The hosted step runs later in `dev-frontend-2`. | not tested |

## How it got there

Each attempt below is the probe call, unless it says diag. The diag calls signed a JWT in anonymous Apex with `Auth.JWT`, `Auth.JWS` (the same org certificate) and `Auth.JWTBearerTokenExchange`, to separate app problems from credential problems. They printed only the status and whether a token came back, never the token.

| # | Change | Result |
| --- | --- | --- |
| 1 | First full deploy. `iss`, `aud` and `sub` written as JSON strings (`"..."`), scopes `Api` | `Unable to complete the JWT token exchange. Error: invalid_client_id. Error description: client identifier invalid.` |
| 2 | Waited three minutes | The same |
| check | `GET /services/oauth2/authorize` with the key | `missing required code challenge`, so the org knows the client id |
| 3 | Added the app policy file (`isEnabled`, `isOauthPluginEnabled`) | The same `invalid_client_id` |
| diag | `aud` = My Domain, `https://test.salesforce.com`, `https://login.salesforce.com` | The first two: `invalid_request`, `refresh_token scope is required and the connected app should be installed and preauthorized.` The third: `invalid_grant`, `audience is invalid`. |
| fix | App scopes `Api, RefreshToken` | diag: My Domain and `https://test.salesforce.com` both 200 with a token. `https://login.salesforce.com` still `audience is invalid`. |
| 4 | Probe again, claims still JSON strings | `invalid_client_id` |
| 5 | `iss` without quotes | `invalid_grant`, `user hasn't approved this consumer.` |
| 6 | `sub` without quotes: `{!$User.Username}` | 200 on all four paths |

Then the probe was removed, set up again from a clean org with the script, and passed on the first call. It was removed again at the end.

## Findings

| Finding | What it means for the build |
| --- | --- |
| The JWT bearer flow needs the `RefreshToken` scope on the app, even though no refresh token is used. Without it the token endpoint answers `refresh_token scope is required and the connected app should be installed and preauthorized.` | The app's scopes are `Api, RefreshToken`. The external credential sets no scope of its own. |
| Claim values are used as written. A JSON-quoted `iss` is sent with its quotes (`invalid_client_id`), and a quoted `sub` is not evaluated as a formula (`user hasn't approved this consumer.`). `aud` is the exception: the deploy refuses an unquoted URL with `The JWT aud claim has invalid JSON syntax.` | `iss` is the bare consumer key, `sub` is the bare formula `{!$User.Username}`, `aud` is `&quot;https://<My Domain>&quot;` in the XML. |
| The protocol variant parameter is named after the protocol: `parameterName` `Oauth`, `parameterType` `AuthProtocolVariant`, `parameterValue` `JwtBearer`. The name `AuthProtocolVariant` is refused: `The ParameterName for AuthProtocolVariant is invalid. This authentication protocol requires it to be Oauth.` | Recorded in the metadata below. |
| The org adds the other claims itself: `iat`, `nbf`, `exp` (now plus 120 seconds) and the header claims `typ` `JWT`, `alg` `RS256`, `kid` (the certificate name). | They need not be in the metadata. |
| For a scratch org, `aud` may be the My Domain URL or `https://test.salesforce.com`. `https://login.salesforce.com` is refused (`audience is invalid`). | Use the My Domain URL: it is right for every kind of org. That is the script's default. |
| A Certificate deploys from source only with a content file. An empty `.crt` makes the org generate a new self-signed key pair (2048-bit, expiring a year later). Retrieving it gives the public certificate only. | Each org gets its own key, and nothing private is in the repo. The certificate must be renewed yearly, and the app's `certificate` updated with it. |
| The app's consumer key comes from `GET /services/data/v68.0/apps/oauth/credentials/<app id>`, whose listing holds `id`, `key`, `name` and `url` per consumer and no secret. | The setup reads the key without any secret setting or permission. |
| The External Client App has PKCE on for the authorization code flow, whatever the file says. | It does not matter here: the JWT flow has no browser step. |
| A user without the permission set gets `System.CalloutException: We couldn't access the credential(s). You might not have the required permissions, or the external credential "SalesforceReportsSelf" might not exist.` | The door can map this message to a clear error with a hint to assign the permission set. |
| A callout after uncommitted DML fails: `System.CalloutException: You have uncommitted work pending. Please commit or rollback before calling out` (`scripts/dml-first.apex`). | The same rule as for the session callout. The tools do no DML before they call out, so nothing changes. |
| `sf project deploy start` and the destructive deploy hit source-tracking conflicts in the scratch org after a removal. | The scripts pass `--ignore-conflicts`. |
| The four calls in one transaction used 4 of 100 callouts. Whether the token is minted once per transaction or per call was not measured. | Inferred: one exchange per call at worst. A tool makes at most a few calls. |

## The metadata that worked

All names are `SalesforceReportsSelf`. Placeholders are shown as the tracked files hold them.

External credential:

```xml
<ExternalCredential xmlns="http://soap.sforce.com/2006/04/metadata">
    <authenticationProtocol>Oauth</authenticationProtocol>
    <externalCredentialParameters>
        <parameterName>Oauth</parameterName>
        <parameterType>AuthProtocolVariant</parameterType>
        <parameterValue>JwtBearer</parameterValue>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <parameterName>AuthProviderUrl</parameterName>
        <parameterType>AuthProviderUrl</parameterType>
        <parameterValue>https://__MY_DOMAIN__/services/oauth2/token</parameterValue>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <certificate>SalesforceReportsSelf</certificate>
        <parameterName>SigningCertificate</parameterName>
        <parameterType>SigningCertificate</parameterType>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <parameterName>iss</parameterName>
        <parameterType>JwtBodyClaim</parameterType>
        <parameterValue>__CONSUMER_KEY__</parameterValue>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <parameterName>aud</parameterName>
        <parameterType>JwtBodyClaim</parameterType>
        <parameterValue>&quot;__AUDIENCE__&quot;</parameterValue>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <parameterName>sub</parameterName>
        <parameterType>JwtBodyClaim</parameterType>
        <parameterValue>{!$User.Username}</parameterValue>
    </externalCredentialParameters>
    <externalCredentialParameters>
        <parameterName>RunningUser</parameterName>
        <parameterType>PerUserPrincipal</parameterType>
        <sequenceNumber>1</sequenceNumber>
    </externalCredentialParameters>
    <label>Salesforce Reports Self (probe)</label>
</ExternalCredential>
```

Named credential: `namedCredentialType` `SecuredEndpoint`, `calloutStatus` `Enabled`, `generateAuthorizationHeader` true, both merge-field flags false. Parameter `Url` (type `Url`) is `https://__MY_DOMAIN__`. Parameter `ExternalCredential` (type `Authentication`) names the external credential.

Permission set: one `externalCredentialPrincipalAccesses` entry, `enabled` true, `externalCredentialPrincipal` `SalesforceReportsSelf-RunningUser`. No object permission was needed: the user needed no access to `UserExternalCredential`.

External Client App, in four more files:

| Type | Fields set |
| --- | --- |
| `ExternalClientApplication` | `distributionState` `Local`, `isProtected` false, label, contact email |
| `ExtlClntAppOauthSettings` | `commaSeparatedOauthScopes` `Api, RefreshToken` |
| `ExtlClntAppGlobalOauthSettings` | `certificate` (the public PEM), a callback URL (unused), PKCE, secret and rotation flags false. No key or secret. |
| `ExtlClntAppConfigurablePolicies` | `isEnabled` true, `isOauthPluginEnabled` true. It was added before the scope fix, so whether it is needed was not isolated. |
| `ExtlClntAppOauthConfigurablePolicies` | `permittedUsersPolicyType` `AdminApprovedPreAuthorized`, `commaSeparatedPermissionSet` `SalesforceReportsSelf`. The org filled in its defaults for the rest. |

## What the setup script fills

`scripts/setup.sh <alias> [audience]` copies the project to a temp folder, fills it, deploys in six steps and deletes the copy. It prints no filled value.

| Step | What |
| --- | --- |
| 1 | Deploy the certificate. The org makes the key pair. |
| 2 | Retrieve the certificate's public part, and fill `__CERTIFICATE__` in the app's global OAuth settings. |
| 3 | Deploy the app, its scopes, its global OAuth settings and its app policy. |
| 4 | Read the consumer key from `apps/oauth/credentials/<app id>`, and fill `__CONSUMER_KEY__`, `__MY_DOMAIN__` (from `sf org display`) and `__AUDIENCE__` (default `https://<My Domain>`). |
| 5 | Deploy the external credential, the named credential and the permission set. |
| 6 | Deploy the app's OAuth policy, which names the permission set. It goes last because it needs the permission set. |

## Recommendation for the build

Give `ReportsCallout` a third identity, `NAMED_CREDENTIAL`, and set it on the hosted route instead of `NONE`.

| Piece | How |
| --- | --- |
| `ReportsCallout.Identity` | `SESSION`, `NAMED_CREDENTIAL`, `NONE`. The REST door keeps `SESSION`. The hosted door sets `NAMED_CREDENTIAL`. |
| `send` | For `NAMED_CREDENTIAL`, set the endpoint to `callout:<name>` plus `API_PATH` plus the path, and set no `Authorization` header: the credential adds it. Everything after the send (status mapping, `toError`) stays as it is. |
| Errors | Map a `CalloutException` whose message starts `We couldn't access the credential(s)` to a new code such as `CALLOUT_CREDENTIAL`, with a hint to assign the permission set. Map `Unable to complete the JWT token exchange` to the same code with the Salesforce error text kept, since it names the setup fault. |
| Shipping | The credential, the app, the certificate and the permission set are one more unit, beside `mcp-app`, with its own setup script that fills the same four values, and its own destructive manifests. The certificate must be made in each org. Or fold the principal access into the existing read permission set, so one assignment covers both. |
| Tests | An `HttpCalloutMock` sees the `callout:` endpoint, so the tests can assert the endpoint and the missing header. The JWT exchange itself cannot run in a test. |
| Order in a tool | Call out before any DML, as today. |

Not decided here: whether the hosted route should fall back to `NONE` when the credential is missing, or always answer the credential error.

## Not tested here

| Item | Why |
| --- | --- |
| The callout from a hosted MCP sign-in | It needs a sign-in in claude.ai. It runs later in `dev-frontend-2`. The named credential mints its own token from the running user's username, so it should not depend on how the user signed in. That is inferred until the hosted run. |
| A user other than the org's default user | `dev-backend` has one usable user. |
| An org other than a scratch org | Production and sandbox orgs are inferred to behave the same, with My Domain as `aud`. |
| Certificate renewal | The certificate expires a year after setup. Renewing means a new certificate and the app's `certificate` updated; not run. |
