## What was built

| Piece | What it does |
| --- | --- |
| `create_report` | Reads `name` (1 to 40 characters), `description`, `folderId` and `fromReportId`. From a definition, it needs `reportType` and maps the definition in full. From `fromReportId`, it reads the saved report's REST describe through the callout, maps the given fields as a partial definition, and applies them as the local `applyChanges` does: it drops the old report's id, developer name, folder and name, infers the format from the groupings unless one is given, takes grouped columns out of the detail columns, and adds each new aggregate's column. Both paths then add a detail column to a grouped report that has none, as `query_report` does. It posts to `/analytics/reports` and answers `{id, name, folder, folderId, url, summary, notes}`. |
| `update_report` | Builds the patch from the given fields only (a partial definition plus `name`, `description` and `folderId`). An empty patch answers 400 "Nothing to update. Give at least one field to change." before any callout. When `aggregates` comes without `columns`, a new aggregate's column is appended to the saved detail columns. It sends `PATCH /analytics/reports/{id}` and answers `{summary, changes, notes}`, one `changes` line per field sent, as the local tool writes them. |
| `clone_report` | `POST /analytics/reports?cloneId={id}` with the optional `name` and `folderId`. It answers `{id, name, folder, folderId, url}`. |
| `ReportsApi.requireWrite` | The permission check, run before the input is parsed. |
| `ReportsSummary.summarizeReportJson` | The summary over the REST describe JSON that the save calls answer with, as `src/reports/summarize.ts` reads it. |
| `ReportsApi.sortedJson` | Writes a `changes` value as JSON with object keys sorted. See the finding below. |
| `Reports_MCP_Write` (custom permission) and `Salesforce_Reports_MCP_Write` (permission set) | New metadata. The permission set grants only the custom permission. The destructive manifests name both, and `ReportsSaveTest`. |
| `door-tools.ts` | Lists eleven tools. A new `toolFlags` gives each tool's ReadOnly, Destructive, Idempotent and OpenWorld from the local annotations. The generator and the setup script both use it, so the save tools are not marked read-only. The tool list is read from the local server in write mode, without delete. |
| `generate-metadata.ts` | The save operations also document a `403` response. The server description says that saving needs the write permission set. |
| `scripts/live-check.ts` | The save steps run through the door. Only the delete stays local. |
| `scripts/parity-check.ts` | Five new cases on both doors, and the apex 404 case now uses `delete_report`. |

### Findings

| Finding | What it means here |
| --- | --- |
| A map from `JSON.deserializeUntyped` loses the key order of the response. `JSON.serialize` of it writes the keys in another order. | The local `changes` lines are `JSON.stringify` of Salesforce's objects, in the response's order, and Salesforce writes keys in alphabetical order. The door writes them with keys sorted, so a line such as `reportFilters: [{"column":...,"operator":...,"value":...}]` matches. The unit test for `update_report` caught it. |
| In an Apex test, a callout made inside `System.runAs` fails with "You have uncommitted work pending" unless `Test.startTest()` runs first inside the `runAs` block. | `ReportsSaveTest` wraps each test body in `System.runAs(...)` then `Test.startTest()`. |
| `dev-frontend-2` uses both of its Salesforce licenses. | The test user without the permission is a Chatter Free user, which takes no Salesforce license. The writer is the running user, with the write permission set assigned in the test setup when it lacks one. |

## Listing the save tools

The decision: the three save tools are listed for every user of the hosted server, and the door refuses a user without `Reports_MCP_Write` with `WRITE_NOT_ALLOWED`.

Per-user hiding on one hosted server is not possible. The Tooling objects behind a hosted server carry no user or permission scope:

| Object | Fields that matter |
| --- | --- |
| `McpServerDefinition` | the server's name, label and description |
| `McpServerToolDefinition` | `ToolName`, `ToolTitle`, `DescriptionOverride`, `ReadOnly`, `Destructive`, `Idempotent`, `OpenWorld`, `ReturnDirect`, `UiResource` |
| `McpServerToolApiDefinition` | `ApiSource`, `ApiIdentifier`, `Operation` |
| `McpServerAccess` | `Active`, `McpServerId` |

The only MCP field on `PermissionSet` is `PermissionsMCPMetadataApi`, which is about the metadata API, not a server's tools. There is no `SetupEntityAccess` type for an MCP server or tool, so a permission set cannot grant one. Whether hosted MCP filters `tools/list` by Apex class access is untested. It would not help: one class, `ReportsApi`, serves all eleven tools, so it would hide all of them or none. A second server for the save tools would have the same problem, because `McpServerAccess` is not scoped to users either.

## Parity

`npm run parity -- --org dev-frontend-2`. Each case runs on both doors and the JSON is compared deeply (object key order is ignored, array order is not).

The save cases create real reports, one per door. Their answers must differ in a few fields, so both are normalized before the compare:

| Normalized | How | Where it shows |
| --- | --- | --- |
| Report ids | Any `00O` id in a string becomes `<report id>` | `id`, `summary.id`, and inside `url` and `summary.url` |
| Names | The door token in the name (`-local-` or `-apex-`) becomes `-<door>-` | `name`, `summary.name`, and the `name:` line of `changes` |
| Developer names | Every `developerName` value becomes `<developer name>` | `summary.developerName` |

The save answers have no timestamps, so none are normalized. `folderId` and `folder` are not normalized: both doors save as the same user, into the same Private Reports folder. Every report a case creates is deleted through the local server at the end of the run, and a last case checks that no `zz-parity` report is left.

| Case | Result |
| --- | --- |
| The 22 phase 1 cases: run_report (as saved, detail rows, overrides, maxRows cut), describe_report, search_reports, list_report_folders, combine_reports stack and join | match |
| The 18 phase 3a cases: describe_report_type, list_report_types, query_report, combine_reports with definitions | match |
| create_report from a definition (a summary with a filter) | match |
| create_report from fromReportId with a change (a grouping and aggregates on a tabular copy) | match |
| update_report: name, filters, and an aggregate on a column the report lacks | match |
| clone_report | match |
| update_report with nothing to change: both doors fail with the same error body | match |
| apex only: delete_report answers 404, query_report without reportType answers 400, an unknown tool answers 404, a bad report id answers 400 | as expected |
| no zz-parity report left behind | none left |

The red run before the change (`.delegation/BE-7/red-1.txt`, not committed) had every earlier case matching and the five new cases failing: the four saves with 404 `UNKNOWN_TOOL` from the door, and the update with nothing to change on its error code.

## Open: does the callout work under a hosted MCP sign-in?

Still open, as in [phase 3a](v0.2-phase3.md). The save tools call out the same way as `list_report_types` and `query_report`, so the same question decides them. The External Client App is unchanged.

### Ben's steps

1. In claude.ai, open a chat with the SalesforceReports connector on (the one connected in phase 2 to `dev-frontend-2`). If it is not connected, follow steps 6 and 7 of "In the org" in the repo README first.
2. If the connector does not list `create_report`, `update_report` and `clone_report`, open Settings, then Connectors, then SalesforceReports, and reconnect. If tools still fail as inactive, open Setup in the scratch org, go to API Catalog, open `ReportsApi`, select all eleven operations, and click Activate. Then reconnect.
3. Ask: "Using the SalesforceReports connector, call list_report_types with search opportunit." Done looks like a list that includes the type `Opportunity`.
4. Then ask: "Call query_report with reportType Opportunity, groupingsDown STAGE_NAME and aggregates RowCount." Done looks like a group table by stage.
5. Then ask: "Call create_report with name zz-hosted-check, reportType Opportunity, groupingsDown STAGE_NAME and aggregates RowCount." Done looks like an answer with an id that starts with `00O`, folder Private Reports, and a link. The signed-in user needs `Salesforce_Reports_MCP_Write`; without it, done looks like `WRITE_NOT_ALLOWED`.
6. Delete that report: open its link and delete it in Salesforce, or call `delete_report` on the local server.
7. Write down the answers of steps 3 and 5: a list of types and a saved report, or an error with its code.

An answer with code `CALLOUT_SESSION` means the Apex ran but the org's REST API refused the session from the hosted sign-in. The two fixes in the phase 3a doc apply unchanged: add the `Api` scope to the External Client App, or a per-user Named Credential used by `ReportsCallout`. Neither is made here.
