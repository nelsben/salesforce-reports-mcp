## 1. Hosted MCP on a scratch org

**Answer.** Yes for the types. Open for an end-to-end call.

**Evidence.**

```
sf org display -o dev-backend        Edition: Developer   Api Version: 68.0
sf org list metadata-types -o dev-backend --json
  McpServerDefinition   mcpServerDefinitions
  CatalogedApi, CatalogedApiVersion, CatalogedApiArtifactVersionInfo
  ExternalServiceRegistration, NamedCredential, ExternalCredential, RemoteSiteSetting
```

Tooling API sObjects exist for the server: `McpServerDefinition`, `McpServerToolDefinition`, `McpServerToolApiDefinition`, `McpServerResourceDefinition`, `McpServerPromptDefinition`, `McpServerAccess`.

The metadata type is tiny. `describeValueType` for `McpServerDefinition` returns only `description`, `masterLabel` and `fullName`. This deployed on the first try:

```
sf project deploy start -d force-app/main/default/mcpServerDefinitions -o dev-backend
  Status: Succeeded   Created ReportsProbe McpServerDefinition
sf data query -t -q "SELECT Id, DeveloperName, MasterLabel FROM McpServerDefinition" -o dev-backend
  1g1Aw00000004YHIAY | ReportsProbe | Reports Probe
```

The Apex REST class deployed and answers:

```
sf api request rest "/services/apexrest/reportsprobe/v1/ping" -o dev-backend
  { "userName": "<scratch user>", "message": "pong" }
```

Tools are not part of the metadata type. They are rows in `McpServerToolDefinition` (`ToolName`, `ToolTitle`, `DescriptionOverride`, `ReadOnly`, `Destructive`, `Idempotent`, `OpenWorld`) with a child `McpServerToolApiDefinition` (`ApiSource` one of `CONNECT`, `CLASSIC`, `API_CATALOG`, `AGENT`; `ApiIdentifier`; `Operation`). I did not create these rows. Writing them through the Tooling API is a data write, not a deploy of a probe component, and the session's guard refused it. So no tool was attached to the server, and I did not see a tool list.

An MCP call was tried with the CLI access token:

```
POST https://api.salesforce.com/platform/mcp/v1/custom/ReportsProbe   -> 401 {"errors":[{"message":"Invalid token"}]}
```

The URL shape is second-hand (search summaries, not Salesforce docs, which answered 403). The 401 says the CLI token is not accepted at the hosted endpoint.

**What Ben would do to finish this (open).**

1. In Setup, create an External Client App with OAuth enabled, a callback URL for the MCP client, and the `mcp_api` style scopes the hosted MCP docs list (confirm the exact scope names there).
2. In Setup, open the MCP server `Reports Probe`, add a tool, choose the Apex REST source, and pick the probe operation. Activate the server.
3. Add the server to Claude as a custom connector with the External Client App's consumer key, and sign in.
4. Ask Claude to call the tool. Done looks like `pong` and the user name coming back.

**What it means.** Phase 1 (REST door) is not blocked. Phase 2 (MCP door) can ship the `McpServerDefinition` and the permission set as source, but the tool rows and the OAuth app are admin steps that the README must spell out. The in-org runner rehearsal needs Ben at the keyboard once.

## 2. From Apex class to tools

**Answer.** Open, leaning yes. The class does not become tools by itself. An OpenAPI document registered as an `ExternalServiceRegistration` with provider type `ApexRest` is the route that produced named operations.

**Evidence.** It took several tries. The errors are the useful part:

| Try | Error |
| --- | --- |
| `<status>Complete</status>` in the XML | `Unable to create/update fields: Status` (the field is read-only) |
| `<systemVersion>1</systemVersion>` | `registration version 1 isn't valid. Expected versions 2, 3, 4, 5, 6, 7, 8, 9` |
| `servers: - url: /services/apexrest/reportsprobe/v1` | `If the registration provider type is ApexRest, the base path in the spec must be /services/apexrest` |
| No provider asset | `Enter a RegistrationProviderAsset. This value is required if the registrationProviderType is ApexRest, AuraEnabled, or NamedQuery` |

The version that deployed uses `systemVersion` 3, `registrationProviderAsset` set to the Apex class name, base path `/services/apexrest`, the path `/reportsprobe/v1/`, and `operationId: run_report_probe`. A first attempt with the schema as a separate `.yaml` file and `schemaUploadFileName` was accepted but stored no schema (`SchemaType` null, `Status` Incomplete), so the schema goes inline in `<schema>`.

Retrieved back from the org:

```
<operations>
    <active>false</active>
    <name>runx5freportx5fprobe</name>
</operations>
```

So the operation name comes from our `operationId`, with `_` encoded as `x5f`. The operation is inactive. Deploying `<active>true</active>` returned Succeeded but the retrieve still showed `false`, so activation is not a metadata step.

Salesforce's own route to the YAML is the VS Code command "SFDX: Create OpenAPI Document from This Class", which writes `<Class>.yaml` and an `externalServiceRegistration` file (second-hand: search summaries). It is off by default for `@RestResource` and uses an AI service. I did not run it. There is no org endpoint that generates the document: `/services/data/v68.0/apex-rest-openapi`, `/openapi`, `/async-api` and `/apex/openapi` all answer 404.

I could not see the tool names and input schemas that the hosted server publishes, because no tool row was attached (probe 1). Input schemas for a `GET` come from the OpenAPI `parameters`, and for a `POST` from `requestBody`, as written in our own document.

**What it means.** We write the OpenAPI document ourselves, so tool names like `run_report` and `search_reports` are ours, set by `operationId`. One Apex REST class has one `@HttpGet`, one `@HttpPost` and so on, so the tools must either be paths under one verb dispatched in Apex (as the lab class does) or sit behind `@HttpPost` with a body. Phase 2 must verify the final tool names in a live server before the skill text is changed.

## 3. A callout to the org's own REST API

**Answer.** Yes. No Remote Site Setting and no Named Credential were needed. Under a hosted MCP sign-in it is open.

**Evidence.** The lab class calls `URL.getOrgDomainUrl().toExternalForm() + path` with `Authorization: Bearer UserInfo.getSessionId()`. The org's two existing Remote Site Settings are unrelated to its own domain, and I did not deploy one.

```
GET  /services/data/v62.0/analytics/reportTypes          -> status 200, 12 categories, 52,295 bytes
POST /services/data/v62.0/analytics/reports/query        -> status 200, 3,804 bytes (Opportunity summary by stage)
POST /services/data/v62.0/analytics/reports  (create)    -> status 200, id prefix 00O
DELETE /services/data/v62.0/analytics/reports/<id>       -> status 204
```

Each was invoked with `sf api request rest "/services/apexrest/reportsprobelab/v1/<op>" -o dev-backend`. The first query failed with `You can't include groupings in the selected columns list`, which was my test body and not a platform limit.

This ran under the CLI session, which is a user session for the running user. It does not show what `UserInfo.getSessionId()` returns for a user signed in through a hosted MCP client. That token can be an OAuth access token with limited scopes, and Apex may return a session that cannot call the Analytics REST API. This is open, and the steps are the ones under probe 1, then call the lab `types` operation as a tool.

**What it means.** Phase 3 can use `query_report` and the save tools with plain callouts under the CLI or a normal user session. Whether they work under MCP depends on the open sign-in test. If they do not, saving stays local-only, as design.md already allows.

## 4. Heap and CPU

**Answer.** Estimated, not measured at scale: the org holds 1 opportunity, 2 accounts and 7 users, and I was not allowed to create records.

**Limits seen.** `Limits.getLimitHeapSize()` returned 10,000,000 and `getLimitCpuTime()` returned 10,000 inside the REST call. Salesforce's documented synchronous heap limit is 6 MB (from memory, not fetched). Plan against 6 MB.

**Real runs** (`Reports.ReportManager.runReport(id, true)` on a saved tabular User report, shaped to JSON; heap before the call was about 6.8 KB):

| Rows | Columns | Cells | Heap added by the run | Heap after shaping | JSON bytes | CPU ms for the run |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 4 (Opportunity) | 4 | 2,457 | 9,664 | 418 | 94 |
| 4 | 3 | 12 | 2,504 | 9,701 | 432 | 85 to 87 |
| 4 | 10 | 40 | 1,326 to 3,401 | 9,274 to 10,934 | 1,046 | 89 to 99 |
| 4 | 30 | 120 | 7,951 to 8,282 | 16,582 to 16,814 | 3,933 | 42 to 147 |

Slope: about 50 bytes of heap per cell for the run result. CPU does not trend with cells at this size. It is 40 to 150 ms and noisy, so the run's own CPU at 200,000 cells is unknown.

**Synthetic shaping** (the same `columns` and `rows` structure built from generated cells, then `JSON.serialize`):

| Rows | Columns | Cells | Heap after shaping | JSON bytes | CPU ms shaping | CPU ms with JSON |
| --- | --- | --- | --- | --- | --- | --- |
| 200 | 20 | 4,000 | 183,590 | 40,861 | 22 | 43 |
| 500 | 100 | 50,000 | 2,207,850 | 522,201 | 224 | 460 |
| 1,000 | 100 | 100,000 | 4,409,352 | 1,064,018 | 462 | 926 |
| 2,000 | 100 | 200,000 | 8,862,351 | 2,211,018 | 888 | 1,736 |

Shaping costs about 44 bytes of heap and 4.4 microseconds of CPU per cell, and the JSON string adds about 11 bytes and 4.2 microseconds per cell.

**Estimate for 2,000 rows by 100 columns (200,000 cells).**

| Part | Heap |
| --- | --- |
| Run result, 50 bytes per cell | about 10 MB |
| Shaped structure, 44 bytes per cell | about 8.9 MB |
| JSON string | about 2.2 MB |
| Peak | about 19 to 21 MB against 6 MB (10 MB as reported) |

CPU is about 1.7 s for shaping and JSON, which fits 10 s. The run's own CPU is the open part.

**What it means.** The full run does not fit, by a factor of 2 to 3.5. At about 105 bytes per cell, 6 MB holds about 57,000 cells. Use a 50,000-cell budget:

| Columns | `maxRows` ceiling |
| --- | --- |
| 10 | 2,000 |
| 25 | 2,000 |
| 50 | 1,000 |
| 100 | 500 |

The rule for the in-org `maxRows` is `min(2000, floor(50000 / columns))`, and the default stays 200 (a 200 by 100 run is 20,000 cells, about 2.1 MB). The shaper should add the usual note when it cuts rows. Phase 1 should re-measure on a seeded org (`dev-frontend-2` is the seeded one) before the number is final, and should drop references to the run result as soon as shaping is done.

## 5. Report type columns without a callout

**Answer.** Yes.

**Evidence.** `Reports.ReportManager.describeReport(id).getReportTypeMetadata().getCategories()` returns the report type's columns by section. For the Opportunity type: 9 sections, 109 columns (35, 13, 20, 16, 3, 4, 16, 1, 1). Each column gives `getName()`, `getLabel()` and `getDataType()`.

```
Opportunity Information | CREATED       | Created By      | STRING_DATA
Opportunity Information | CREATED_ALIAS | Created Alias   | STRING_DATA
Opportunity Information | LAST_UPDATE_BY| Last Modified By| STRING_DATA
```

Compared with `GET /services/data/v62.0/analytics/reportTypes/Opportunity` (67,428 bytes):

| | Apex `describeReport` | REST `reportTypes/Opportunity` |
| --- | --- | --- |
| Columns | 109 | 109 |
| Same column names | yes, no differences | yes |
| Sections | by label, same counts | same |
| Data types | `STRING_DATA`, `CURRENCY_DATA`, `PICKLIST_DATA` and 10 more | `string`, `currency`, `picklist` and 10 more (lower case, no `_DATA`) |
| Extra in REST | | `filterable`, `bucketable`, `filterValues`, `isLookup`, `maxLength`, `fullyQualifiedName`, plus `dataTypeFilterOperatorMap`, `scopeInfo`, `standardDateFilterDurationGroups` |

The same held for the User type (12 sections, 131 columns, the same counts as REST). The Apex `ReportTypeMetadata` has no `getDataTypeFilterOperatorMap()` (compile error), and I did not check for the other extras.

**What it means.** `describe_report_type` is enough for the column list: name, label, data type, section. It is not enough for filter operators or picklist values. The catch is that `describeReport` needs a saved report of that type, so for a type nobody has a report on, the tool needs a callout (probe 3) or must say so. Map the data type by lower-casing and removing `_DATA`.
