# v0.3 dashboards: what the REST API does

Run on 2026-10-16 against `dev-frontend-2`: a Developer Edition scratch org, API v62.0 for every call (the server's default), org API 68.0. The dashboard is `Pipeline_Overview`, deployed from [`probes/v0.3-dashboards`](../../probes/v0.3-dashboards/README.md). It has eight components over three Opportunity summary reports, one filter (Stage) with three options, and runs as a specified user. The first probe (the dashboard kit, the list endpoint, the first refresh, the once-a-minute limit) was run by hand a day earlier. Findings from that run are marked "first probe": the requests were not repeated, so there are no new timings for them.

Paths below start after `/services/data/v62.0`. Ids are shown as `<dashboardId>`, `<filterId>` and `<optionA>`, `<optionB>`, `<optionC>` (Prospecting, Negotiation/Review, Closed Won). Responses are trimmed.

## Summary

| Question | Answer |
| --- | --- |
| Does `GET /analytics/dashboards` find a dashboard? | No. It lists only recently viewed dashboards, and returned `[]` for this one, with or without `?q=`. Find dashboards with SOQL on `Dashboard` (below). |
| Does a dashboard that was never refreshed have data? | No. Every component answers `componentDataStatus: NO_DATA`, `refreshDate: null` and `reportResult: null`. |
| How does a refresh work? | `PUT /analytics/dashboards/{id}` answers 201 with a `statusUrl`. Data was ready at the first poll, about 3 seconds after the PUT, in every refresh. |
| How often can a dashboard be refreshed? | Once a minute. A second refresh inside a minute answers 403 `FORBIDDEN` (first probe). Refreshes 70 seconds apart all answered 201. |
| What is in the component data? | Each `componentData[].reportResult` is an ordinary report run: `factMap`, `groupingsDown`, `reportMetadata`, `reportExtendedMetadata`. |
| **Which sequence returns filtered data?** | `PUT /analytics/dashboards/{id}?filter1=<optionId>`, then `GET /analytics/dashboards/{id}?filter1=<optionId>`. The filter goes in the query string of the PUT. No request body shape works. |
| What else do filters do? | The cache is kept per filter value. A refresh for one value leaves the other values cached but marks them `STALE`. A value never refreshed answers `NO_DATA`. |

## Finding dashboards

### The list endpoint

```
GET /analytics/dashboards          200   []
GET /analytics/dashboards?q=Pipeline   200   []
GET /analytics/dashboards/<folderId>   400   [{"message":"insufficient access rights on cross-reference id","errorCode":"INSUFFICIENT_ACCESS"}]
```

The list holds recently viewed dashboards only. `Pipeline_Overview` had not been opened in the Lightning UI (`LastViewedDate` is null), and calls through the REST API did not add it. A dashboard id cannot be replaced by a folder id.

### SOQL on `Dashboard`

```sql
SELECT Id, Title, DeveloperName, FolderName, FolderId, Description, Type, RunningUserId, LastViewedDate, LastModifiedDate
FROM Dashboard
WHERE (Title LIKE '%Pipeline%' OR DeveloperName LIKE '%Pipeline%') AND FolderName LIKE '%Probe%'
ORDER BY LastModifiedDate DESC
LIMIT 25
```

Run with `sf data query -o dev-frontend-2`. It returned one row:

| Field | Value |
| --- | --- |
| `Id` | `<dashboardId>` (`01Z…`) |
| `Title` | `Pipeline Overview` |
| `DeveloperName` | `Pipeline_Overview` |
| `FolderName` | `Dashboard Probe Dashboards` |
| `FolderId` | `00l…` |
| `Description` | `null` |
| `Type` | `SpecifiedUser` (the same value as `dashboardType` in describe) |
| `RunningUserId` | `005…` |
| `LastViewedDate` | `null` |
| `LastModifiedDate` | `2026-10-17T01:32:09.000+0000` |

A title that matches nothing (`Title LIKE '%zzz%'`) returns 0 rows with no error.

"For the signed-in user" is automatic: SOQL on `Dashboard` returns the dashboards the signed-in user can see, not every dashboard in the org. The server builds the `WHERE` the way `search_reports` does, with `soqlLike` on each term. The `Id` goes straight into the REST paths below.

### Components and layout

Each component has `id`, `type` (`Report` for all eight), `header`, `title`, `footer`, `reportId`, `lastModifiedDate`, `componentData` (an index, see below) and `properties`. `properties` holds `visualizationType`, `reportFormat`, `aggregates` (`[{"name":"s!AMOUNT"}]`), `groupings`, `filterColumns` (`[{"label":"Stage","name":"STAGE_NAME"}]`, the columns the dashboard filter applies to), `maxRows`, `sort`, `useReportChart`, `autoSelectColumns` and `visualizationProperties` (colors, break points, display units and similar).

| Header | `visualizationType` | Report | `groupings` | Layout (col, row, span x rows) |
| --- | --- | --- | --- | --- |
| Won to Date | Metric | Won by Stage | none | 0, 0, 3 x 4 |
| Won vs Target | Gauge | Won by Stage | none | 3, 0, 3 x 4 |
| Pipeline Mix | Donut | Pipeline by Stage | `STAGE_NAME` | 6, 0, 6 x 8 |
| Pipeline by Stage | Bar | Pipeline by Stage | `STAGE_NAME` | 0, 4, 6 x 8 |
| Amount by Close Month | Line | Amount by Close Month | `CLOSE_DATE` | 6, 8, 6 x 8 |
| Stage Table | Table | Pipeline by Stage | `STAGE_NAME` | 0, 12, 6 x 8 |
| Stage Funnel | Funnel | Pipeline by Stage | `STAGE_NAME` | 6, 16, 6 x 8 |
| Close Month Columns | Column | Amount by Close Month | `CLOSE_DATE` | 0, 20, 6 x 8 |

`layout.components[i]` is the position of `components[i]`; the two arrays line up by index. The table lists the components in describe order. Gauge and metric components have no grouping. The Table component sits on a summary report and still returns a summary, with no detail rows.

`components[i].componentData` is an index into the results' `componentData` array. It matched here, but the results array is not in `components` order in general, so join by `componentId`.

## Results

```
GET /analytics/dashboards/<dashboardId>   200   0.6 to 1.3 s
```

The body has `attributes` (`dashboardId`, `dashboardName`, `describeUrl`, `statusUrl`, `type`), `dashboardMetadata` (the same object as describe), `componentData`, `chatterPhotoUrls` (`{}`) and `picklistColors` (`{}`).

Each `componentData[]` entry:

```json
{
  "componentId": "01a…",
  "status": {
    "componentDataStatus": "DATA",
    "refreshDate": "2026-10-17T02:14:44.000+0000",
    "refreshStatus": "IDLE",
    "errorCode": null, "errorMessage": null, "errorSeverity": null
  },
  "reportResult": { "attributes": {...}, "allData": true, "factMap": {...}, "groupingsDown": {...}, "groupingsAcross": {...},
                    "hasDetailRows": false, "hasExceededTabularRowLimit": false, "reportMetadata": {...}, "reportExtendedMetadata": {...} }
}
```

- `reportResult` is the same shape a report run returns, so `shape.ts` can turn it into a `ReportResult`. Here `hasDetailRows` is false and the `factMap` holds `T!T` and one `n!T` per group, each with `aggregates`.
- `reportResult.reportMetadata` is the source report's own metadata. It does not show the dashboard filter: with `filter1=<optionA>` the `reportFilters` still listed only the report's own `WON equals True`, yet the totals were filtered. A caller must report the dashboard filter itself.
- With no filter, the unfiltered totals were: Won by Stage `$3,629,000`, Pipeline by Stage `$9,322,000` (five or more stages), Amount by Close Month `$9,322,000`.

## No data before the first refresh

A dashboard that was never refreshed answers 200, and every component looks like this (first probe, and reproduced with a filter value that had never been refreshed):

```json
{"componentId": "01a…", "reportResult": null,
 "status": {"componentDataStatus": "NO_DATA", "refreshDate": null, "refreshStatus": "IDLE",
            "errorCode": null, "errorMessage": null, "errorSeverity": null}}
```

There is no error and no hint. The tool has to read `componentDataStatus` and say that the dashboard needs a refresh. `GET .../status` shows the same `NO_DATA` per component.

The no-data fixture was taken with `?filter1=<optionC>` before that value was ever refreshed. The unfiltered dashboard already had data by then, and a redeploy to clear it would change the org. The shape is the same as the unfiltered case. Fixture: [`dashboard-results-no-data.json`](../../test/fixtures/dashboard-results-no-data.json).

## Refresh and status

```
PUT /analytics/dashboards/<dashboardId>          201   0.8 to 1.7 s
{"statusUrl":"/services/data/v62.0/analytics/dashboards/<dashboardId>/status"}

GET /analytics/dashboards/<dashboardId>/status   200
{"componentStatus": [
  {"componentId": "01a…", "componentDataStatus": "DATA", "refreshStatus": "IDLE", "refreshDate": "2026-10-17T02:14:44.000+0000"},
  ...eight entries]}
```

| Check | Result |
| --- | --- |
| Time to data | Every refresh that took effect (the first probe's, and five in this run) was done at the first poll. The poll ran 3 to 9 seconds after the PUT and `refreshDate` was 1 to 6 seconds after it. `refreshStatus` was never seen as anything but `IDLE` or `STALE`. |
| Poll for completion | Poll `.../status` until every entry is `DATA` and `IDLE`, every 3 seconds. This dashboard needed one poll. A larger dashboard may need more; no `RUNNING` value was ever returned, so do not wait for one. |
| Once a minute | A second refresh inside a minute answers 403 `FORBIDDEN`, "You can't refresh this dashboard more than once in a minute." (first probe). In this run PUTs spaced 70 seconds apart all answered 201, and the capture script's spacing of 65 seconds did too. |
| Status of an old value | After a refresh for another filter value, the earlier cache shows `refreshStatus: STALE` with its old `refreshDate`, and still returns its data. |

## Filters: every request tried

Option ids: `<optionA>` Prospecting, `<optionB>` Negotiation/Review, `<optionC>` Closed Won. "Then" is the GET or status call made after the PUT.

### Getting filtered data

| # | Request | Status | Then |
| --- | --- | --- | --- |
| 1 | `PUT /{id}` with body `{"filters":["<optionB>"]}` | 201 | `GET /status?filter1=<optionB>` at +10 s: all `NO_DATA`. `GET ?filter1=<optionB>` at +14 s: all `NO_DATA`. Still `NO_DATA` about 5 minutes later. The first probe saw the same at 70 s. |
| 2 | `PUT /{id}` with body `{"filter1":"<optionB>"}` | 201 | `GET ?filter1=<optionB>` at +11 s: all `NO_DATA` |
| 3 | `PUT /{id}` with body `{"filters":[{"filterId":"<filterId>","optionId":"<optionB>"}]}` | 201 | `GET ?filter1=<optionB>` at +11 s: all `NO_DATA` |
| 4 | `PUT /{id}?filter2=<optionB>` | 400 `BAD_REQUEST` | not applicable |
| 5 | `PUT /{id}?filter1=Negotiation%2FReview` (the option text) | 400 `BAD_REQUEST` | not applicable |
| 6 | **`PUT /{id}?filter1=<optionA>`** | **201** | **`GET /status?filter1=<optionA>` at +17 s: `DATA`, `IDLE`. `GET ?filter1=<optionA>`: `DATA`, filtered.** |
| 7 | **`PUT /{id}?filter1=<optionB>`** | **201** | **`GET /status?filter1=<optionB>` at +9 s: `DATA`, `IDLE`. `GET ?filter1=<optionB>`: `DATA`, filtered.** |

The 400 body in 4 and 5 is `[{"errorCode":"BAD_REQUEST","message":"We can't apply one or more filters because of changes to the dashboard or its source reports."}]`.

A body on the PUT is ignored as far as filters go. Rows 1 to 3 answered 201 and refreshed nothing for the filter. A body shape that means nothing is not an error. (Whether those PUTs refreshed the unfiltered cache was not checked.)

| 10 | `GET /{id}?filter1=<optionB>` after row 7 | 200 | `DATA`. Pipeline by Stage `$1,326,000`, one group `Negotiation/Review`. |
| 11 | `GET /{id}?filter1=<optionC>` (never refreshed) | 200 | all `NO_DATA` |
| 12 | `GET /{id}?filter2=<optionA>` | 400 `BAD_REQUEST` | same message as above |
| 13 | `GET /{id}?filter3=<optionA>` | 400 `BAD_REQUEST` | same message |
| 14 | `GET /{id}?filter1=Prospecting` (option text) | 400 `BAD_REQUEST` | same message |
| 15 | `GET /{id}` (no filter) after row 6 | 200 | `DATA` and totals unchanged ($9,322,000), but `refreshStatus: STALE` |
| 16 | `GET /{id}?filter1=<optionA>` after row 7 | 200 | `DATA` and still filtered, `refreshStatus: STALE` |

### The answer

- **One sequence returns filtered data:** `PUT /analytics/dashboards/{id}?filter1=<optionId>`, wait for `GET /analytics/dashboards/{id}/status?filter1=<optionId>` to show `DATA` and `IDLE`, then `GET /analytics/dashboards/{id}?filter1=<optionId>`. It worked for two of the three options (A and B); the third was kept untouched for the no-data fixture.
- **The first probe's {"filters":[...]} body does not work.** It is accepted and ignored. Waiting longer does not help: the filtered cache stays empty.
- **The option id is required, not its text.** The text answers 400 on PUT and GET.
- **The cache is per filter value.** Each value is refreshed separately and costs one refresh from the once-a-minute allowance. After a refresh for another value, the older caches keep their data and show `STALE`.
- **Only `filter1` was proven.** This dashboard has one filter, so `filter2` and `filter3` answered 400. The query number is most likely the filter's place in `describe.filters`, but a dashboard with two or more filters was not tested.
- **Dashboard filters touch every component.** Here all eight components apply the Stage filter (`filterColumns`), and all eight changed. Rows from a report that does not apply the filter were not tested.

### What the tools should do

- `refresh_dashboard` takes an optional filter choice, matched to an option in `describe.filters` by option id or by `value` text, and sends it as `?filter1=<optionId>` on the PUT. It never sends a body. It refuses a second refresh in a minute before the call, and says so when Salesforce answers 403.
- `run_dashboard` with a filter sends `?filter1=<optionId>` on the GET. When every component is `NO_DATA`, it says the dashboard has no data for that filter and offers `refresh_dashboard` with the same filter. It does not refresh on its own.
- Both say in `notes` when the data is `STALE` and give the `refreshDate`.

## Recapturing the fixtures

```
npm run capture -- --org dev-frontend-2 --dashboard Pipeline_Overview            # reads the cache only
npm run capture -- --org dev-frontend-2 --dashboard Pipeline_Overview --refresh  # also refreshes twice
```

Without `--refresh` the script writes the describe fixture, and the no-data, results and status fixtures when the cache can give them. With `--refresh` it refreshes with the first filter option, waits 65 seconds, then refreshes with no filter, so the org ends with a fresh unfiltered cache. It prints no token.

## Left in the org

Everything this run touched in `dev-frontend-2` is the probe: the dashboard `Pipeline_Overview`, its three reports and the two folders. The dashboard's cache changed by the refreshes (unfiltered, `<optionA>` and `<optionB>` are cached; `<optionC>` is not). Nothing else in any org was created, changed or deleted. Refreshes were sent at least 65 seconds apart.
